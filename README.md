candy-bouquet-bot

Телеграм-бот для продажи букетов из конфет. Внутри бота человек собирает букет сам: выбирает основу, конфеты и их количество, видит состав и итоговую цену, оформляет заказ.

Главное здесь не кнопки, а конструктор. Букет собирается из частей, и не всякий набор можно собрать физически: в основу помещается ограниченное число конфет, а слишком тяжёлый набор она не держит. Поэтому конструктор не просто складывает цену, а проверяет, что собранное действительно можно сделать.

Букеты собираются и продаются вручную с 2025 года (Ferrero Rocher и другие) — бот автоматизирует то, что до сих пор делалось в переписке: подбор состава, расчёт цены, учёт заказов.

Модель данных

Четыре сущности: основа, конфета, букет (состав) и заказ.

Основа ──┐
         ├──> Букет ──> Заказ
Конфета ─┘
Основа (bases)

Корзина, каркас или коробка, в которую втыкаются конфеты. Задаёт оба физических ограничения букета.

Поле	Тип	Описание
id	int, PK	
name	text	«Корзина S», «Коробка 15×15»
slots_total	int	сколько посадочных мест (шпажек) физически есть
max_payload_g	int	сколько граммов основа держит, не теряя форму

photo_file_id	text	file_id фотографии в Telegram
is_active	bool	показывать ли в каталоге
Конфета (candies)

Позиция каталога. Одна конфета может занимать больше одного места — трюфель на шпажке занимает одно, а батончик в обёртке-вееру — два.

Поле	Тип	Описание
id	int, PK	
name	text	«Ferrero Rocher»
brand	text	
unit_weight_g	int	вес одной штуки в граммах
unit_price	int	цена одной штуки, в копейках
slots_per_unit	int	сколько посадочных мест занимает одна штука (обычно 1)
stock_qty	int	остаток на руках
photo_file_id	text	
is_active	bool	
Букет (bouquets + bouquet_items)

Конкретный состав, собранный пользователем. Существует отдельно от заказа: пользователь может собрать букет и не оформить его, а один состав может быть заказан повторно.

bouquets

Поле	Тип	Описание
id	int, PK	
base_id	int, FK → bases	
user_id	int	Telegram user id автора состава
created_at	datetime	

bouquet_items — строки состава

Поле	Тип	Описание
bouquet_id	int, FK → bouquets	
candy_id	int, FK → candies	
qty	int	количество штук, > 0

Первичный ключ — пара (bouquet_id, candy_id): одна и та же конфета не может встретиться в составе двумя строками.

Производные величины (считаются, не хранятся):

used_slots   = Σ item.qty × candy.slots_per_unit
used_weight  = Σ item.qty × candy.unit_weight_g
candies_cost = Σ item.qty × candy.unit_price
total_price  = base.price + candies_cost + markup

Цены хранятся в копейках целыми числами — чтобы на сложении состава не накапливалась ошибка округления.

id	int, PK

user_id	int	Telegram user id покупателя
status	enum	см. ниже
price_total	int	цена, зафиксированная в момент оформления

delivery_note	text	район и способ передачи, без точного адреса в логах

price_total копируется в заказ, а не пересчитывается на лету: цены в каталоге меняются, а покупатель должен заплатить ту сумму, которую видел при оформлении.

Статусы заказа
Статус	Что значит	Куда может перейти
draft	состав собран, заказ не подтверждён	awaiting_payment, cancelled
awaiting_payment	подтверждён, ждём оплату	paid, cancelled
paid	оплата получена	assembling, refunded
assembling	букет собирается	ready, refunded
ready	собран, ждёт передачи	completed, refunded
completed	передан покупателю	— (финальный)
cancelled	отменён до оплаты	— (финальный)
refunded	отменён после оплаты, деньги возвращены	— (финальный)

Правила переходов:

Переходы разрешены только по таблице выше. Любой другой — ошибка, а не «ну ладно».
completed, cancelled и refunded — финальные: из них нет выхода, повтор оформляется новым заказом.
Отмена до оплаты — cancelled, после оплаты — refunded. Это разные вещи в отчётности.
На переходе draft → awaiting_payment остатки конфет резервируются; на cancelled / refunded — возвращаются в stock_qty.
Каждая смена статуса пишет updated_at и строку в журнал — чтобы по заказу было видно историю, а не только текущее состояние.
Ограничения конструктора

Проверяются при каждом изменении состава, до показа цены. Пока хоть одно нарушено — кнопка оформления недоступна.

№	Правило	Почему
1	used_slots ≤ base.slots_total	больше конфет, чем посадочных мест, физически не воткнуть
2	used_weight ≤ base.max_payload_g	перегруженная основа кренится и теряет форму
3	item.qty ≤ candy.stock_qty	нельзя продать то, чего нет на руках
4	состав не пустой: used_slots ≥ 1	
5	не более 4 разных видов конфет	больше — букет выглядит мусорно; ограничение вкусовое, не физическое
6	total_price ≥ min_order_price	букет дешевле минимума невыгоден по времени сборки

Правила 1–4 — жёсткие, нарушать нельзя. 5 и 6 — настраиваемые, лежат в конфиге.

Порядок проверки
on_change(bouquet):
    violations = []
    если used_slots  > base.slots_total   -> violations += «мест: {used}/{total}»
    если used_weight > base.max_payload_g -> violations += «вес: {used}г из {max}г»
    для каждой строки состава:
        если qty > candy.stock_qty        -> violations += «{name}: в наличии {stock}»
    если used_slots == 0                  -> violations += «букет пустой»
    если видов > max_kinds                -> violations += «не больше {max_kinds} видов»
    если total_price < min_order_price    -> violations += «минимум {min} ₽»

    показать состав, цену и violations
    кнопка «Оформить» активна, только если violations пуст

Ошибки показываются все сразу и текстом, а не по одной: человек должен видеть, что именно упирается, а не угадывать перебором.

Пример

Основа «Корзина S»: slots_total = 15, max_payload_g = 400, price = 450 ₽.

Позиция	Шт.	Мест	Вес	Сумма
Ferrero Rocher (12,5 г, 1 место, 65 ₽)	9	9	112 г	585 ₽
Raffaello (10 г, 1 место, 45 ₽)	6	6	60 г	270 ₽
Итого	15	15 / 15	172 / 400 г	1305 ₽

Плюс основа — 1755 ₽. Места заполнены полностью, по весу запас большой: у этой основы раньше упирается именно вместимость. Добавить ещё одну конфету нельзя — сработает правило 1.
